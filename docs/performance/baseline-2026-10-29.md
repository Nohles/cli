## Allocation and parsing costs

Medians of five Go benchmark runs using the synthetic EPUB/CBZ/WAV fixtures.
These exclude HTTP networking/client allocation. B/op measures total allocated
bytes, not retained heap. `open_close` includes eviction/closing the previous
publication and toolkit parsing. The audio serving benchmark is a 64 KiB range.

| Media | Warm route manifest | Warm route asset | Warm cache hit | Open + close | Manifest allocated/op | Asset allocated/op | Open allocated/op |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| EPUB | 1.702 ms | 1.384 ms | 2.660 µs | 1.734 ms | 6,333,130 B | 6,250,904 B | 988,232 B |
| CBZ | 2.257 ms | 1.566 ms | 2.640 µs | 6.613 ms | 6,376,674 B | 6,217,994 B | 18,178,785 B |
| WAV | 1.322 ms | 1.196 ms | 2.621 µs | 0.275 ms | 6,142,765 B | 6,136,808 B | 392,828 B |

Direct warm-cache lookup allocates 840 B/op for all three fixtures. Full routes
allocate about 6.1–6.4 MB/op. In the separate three-second WAV-manifest profile,
`httpcompression.DefaultAdapter` accounts for **99.20% of sampled allocated
bytes cumulatively** (including compressor constructors). Go profiles include
setup and sampling noise, so use this as attribution, not an exact per-request
percentage. CPU samples also show substantial allocation/GC work. The profile's
~17 GB total allocation is cumulative churn, not resident memory.

These small-fixture results are not a production memory ceiling or a suggested
`GOMEMLIMIT`. Each Reader Library can own a separate CLI process, so deployment
memory multiplies with the number of active libraries.

## Optimization candidates and human review

1. **Highest-confidence first change: initialize compression adapters once per
   server/router lifetime.** `pkg/serve/router.go` constructs `DefaultAdapter`
   inside Gorilla middleware application, which runs during request matching.
   This explains the measured multi-megabyte churn even with identity encoding.
   Verify concurrent use, encoding negotiation, Range/HEAD behavior and memory
   before choosing the final implementation. No improvement factor is claimed
   until the unchanged workload is rerun.
2. **Concurrent first opens:** `getPublication` does lookup then parses/inserts
   without coordination of the missing key. Inspection permits duplicate work;
   the eight-client cold CBZ burst has much higher latency than a serial cold
   open. This is evidence to test coalescing, not a measured duplicate-parse
   count. Preserve cancellation, auth/session rights and retain/release safety.
3. **Toolkit comic probes:** the 240-page open allocates ~18.2 MB despite a
   ~3.45 MB archive. The initial dimension-probe budget is 64 KiB/page and ZIP
   ranged reads allocate the requested length before encountering EOF. Test
   smaller progressive probes or length clamping while preserving image
   dimensions and format coverage; do not drop metadata to win a benchmark.
4. **Manifest reuse / cache budgets:** manifests are serialized on each hit.
   The publication cache is currently count-limited (10), not byte-budgeted;
   audio retained blocks and remote ZIP ranges have separate limits. A larger
   count by itself is not a memory-safe improvement. Profile real large media
   before considering a shared byte budget or disk-backed cache.
5. **Human review before changing remote caching:** toolkit
   `pkg/archive/remote.go` stores caller-owned `ReadAt` buffer `p` as cache data
   (`Data: p`). Buffer reuse could corrupt cached bytes. This is an inspection
   concern, not a reproduced failure in these local-media benchmarks. Establish
   a regression test before cache redesign. Also, the CLI's remote-open paths
   pass `NewDefaultRemoteArchiveConfig()` instead of the configured
   `s.remote.Config`; confirm whether exposed cache flags are intended to apply
   there. Do not tune those flags based on the present local-only dataset.

Windows/macOS performance, multi-hour/multifile audiobooks, PDF, selected comic
directories, remote storage, eviction during active streams, idle TTL behavior
and full Reader-to-client latency remain unmeasured. The harness cross-compiles
for Windows amd64 and macOS arm64; that is not an OS runtime qualification.

The Moby-Dick fixture is `../go-toolkit/test/moby-dick.epub` at the toolkit
revision above. The M4B was generated with FFmpeg 4.4.2-0ubuntu0.22.04.1 using the following
commands (different FFmpeg versions may produce different hashes; record them):

```sh
ffmpeg -f lavfi -i 'sine=frequency=440:sample_rate=22050:duration=60' -c:a aac -b:a 64k -movflags +faststart audio.m4b
```

Create an FFmetadata file with `;FFMETADATA1`,
`title=Reader generated chapter benchmark`, then twelve `[CHAPTER]` blocks:
`TIMEBASE=1/1000`, `START=i*5000`, `END=(i+1)*5000`,
`title=Chapter (i+1)` for i=0..11 (write evaluated numbers). Mux it:

```sh
ffmpeg -i audio.m4b -i chapters.txt -map_metadata 1 -map_chapters 1 -c copy -movflags +faststart chapters.m4b
```

Run both HTTP datasets with `--rounds 5 --requests 100 --concurrency 8` and the
same Go environment. Full commands and interpretation are in [README](README.md).

Validation: `go test ./...` passed; harness tests passed under the race detector;
`go vet` passed for the harness/fixtures; harness cross-builds passed for Windows
amd64 and macOS arm64. The CLI was rebuilt to an isolated baseline binary; no
installed executable was replaced. The existing local `go.mod` replacement was
preserved and excluded from the commit. Reader and toolkit production sources
were unchanged.
